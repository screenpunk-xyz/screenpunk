# Screenpunk Mac workbench CLI

`screenpunk`, `screenpunk-service`, and `screenpunk-mcp` are macOS 14+ Swift executables that use one authenticated local broker. `screenpunk-mcp` serves the same closed tool catalog as `screenpunk mcp serve`. Core source, package, device and deployment commands do not require the Mac GUI or preview helper. Run `screenpunk help` for the current command grammar and `screenpunk help TOPIC` for a supported topic.

Start with `screenpunk setup --no-input` to select an existing configured workspace or create the OS-resolved `Documents/Screenpunk` directory. `screenpunk workspace init PATH` creates and selects a visible workspace; `screenpunk workspace open PATH` validates and explicitly selects an existing one. Opening a copied workspace under a fresh local controller home reads its portable catalog and retained history; no separate reindex command or transfer of device authority is involved. `--workspace PATH` on ordinary commands asserts the current selection and never silently switches it. Contained source, settings, attachments and verified package history travel with a complete workspace copy; external sources require explicit rebinding or adoption. Recovery does not transfer Keychain credentials, pairing, approvals, live jobs or installed kits.

The CLI exposes source creation, edits, import/export, builds and build-only watch; package history, verified import/export and library screen mutations; explicit snapshot/relocation and reviewed legacy migration; device pairing/settings/inventory; local connection configuration, scope update and review; exact deployment prepare/review/apply/status/reconcile; service lifecycle and agent tools. `screenpunk operation list` aggregates bounded durable workspace-copy and deployment records but marks coverage incomplete across all operation domains. `screenpunk device logs ID` exposes only bounded broker-observed events, not native device telemetry. `screenpunk doctor` distinguishes observed broker identity/transport from unassessed persistent Keychain identity and OS Local Network authorization.

Connection configuration reads a credential from a controlling terminal or `--secret-stdin` into a fresh broker-owned slot. `connection update` changes an existing grant's reviewed alias/operations while preserving its endpoint and credential; it requires the existing grant generation. Approval remains a separate local terminal or registered GUI review and checks the exact declaration and authorization context before confirmation. MCP exposes the no-credential intent request, while an ordinary authenticated socket client may also stage a scope update. Neither can approve it or read the local-only scope draft. Generic remote revocation is not supported by the device protocol; `connection revoke` and `connection remove` report their local effects.

`screenpunk agent config --client codex|cursor|claude|generic` prints a configuration fragment and never edits agent settings. Invoke the CLI through a stable absolute installed path before copying that fragment. `agent list` reads the same shared tool catalog as MCP `tools/list` without starting a service. `agent test` uses an ordinary broker credential, verifies the selected controller home and tests broker availability without native LAN activation. MCP stdout contains protocol frames only; ordinary CLI `--json` prints one result or error envelope.

Global options include `--json`, `--no-input`, `--workspace PATH`, `--home PATH`, `--runtime-directory PATH`, `--profile NAME`, and `--timeout SECONDS` for supported short requests. A named profile must exist in the selected workspace's portable settings. It overrides only the existing presentation defaults (`theme`, `view`, `sort`, `defaultCollection`); `config get --scope workspace --profile NAME` shows the effective read view, and `--profile default` shows workspace defaults. `config set/unset --scope workspace` edits defaults only; it rejects a named `--profile` instead of silently changing defaults. Screen icon and archive mutations are likewise workspace-wide and reject a named profile. Named-profile writes have no CLI route. Profiles never choose a workspace, endpoint, credential, kit, device or approval. Mutating and long-running commands apply their own bounded deadlines. `service start` runs the packaged sibling service; `service enable|disable` and install/update/uninstall require the reviewed installed-service and release controls. Installed required-kit resolution fails closed until an authenticated production catalog, signer/publisher trust and verified kit are registered. The source tree and private synthetic tests do not qualify a signed/notarized clean-Mac install, real Keychain/Local Network behavior, persistent launchd, physical devices or live deployment.

For an authenticated standalone release, installation verifies the signed manifest and native executable identities, then accepts its measured signed catalog and imports embedded authoring kits before selecting the service. The installed service registers that same compiled signer, channel, and exact publisher policy only when its running executable matches the verified selected release. A missing required kit can be reimported from that retained release without network access, subject to the signed catalog pin, archive hash, strict inventory, and native signature checks.

Build and test with private scratch paths. The repository's focused CLI tests use private `/private/tmp` workspaces, homes and Unix sockets. Full service-start tests may skip their live-owner branch if another legacy writer holds the production owner boundary; such skips are not runtime acceptance. The Mac GUI preview remains available through its separate compatibility path, and optional screenshot tools report unavailability when a compatible verified helper is absent.
