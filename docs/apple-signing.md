# Apple signing for Screenpunk

The native source targets are `ScreenpunkiOS` (iPhone and iPad), `ScreenpunkMac`, and the embedded `ScreenpunkPreviewHost`. The Mac bundle also carries the `screenpunk-mcp` executable and AuthoringKit Node/esbuild binaries. The public Apple Developer Program team is Screenpunk, Inc. (`77KASWDGM6`) in `config/apple-team.xcconfig`. All three XcodeGen specs use that file, enable automatic Apple Development signing for normal local app builds, and the release scripts read the same ID and reject a conflicting environment override. Unsigned CI/source-only tests explicitly pass `CODE_SIGNING_ALLOWED=NO`. Do not treat an unsigned CI build or the unsigned diagnostic DMG as a distribution release.

| Output | Development signing | Current distribution path | Required distribution identity |
| --- | --- | --- | --- |
| iPhone/iPad app, bundle ID `xyz.screenpunk.ios` | Apple Development with a matching development profile or Xcode-managed signing | `.github/workflows/ios-testflight.yml` exports an IPA; optional TestFlight upload, no App Store submission | Apple Distribution and an exact App Store distribution profile for the team and bundle ID |
| Mac app, bundle ID `xyz.screenpunk.macos` | Apple Development or Xcode-managed local signing | `.github/workflows/macos-release.yml` signs a hardened-runtime app and nested executables, notarizes/staples a DMG | Developer ID Application for direct distribution outside the Mac App Store |
| Preview Host, bundle ID `xyz.screenpunk.preview-host` | Apple Development when built independently | Embedded and signed inside the direct-distribution Mac app | Same Developer ID Application team as containing app |
| Standalone `screenpunk`, `screenpunk-mcp`, `screenpunk-service` | Local source builds are not release artifacts | `tools/screenpunk-distribution/build-local-test-distribution.sh` currently makes an incomplete unsigned test unit only | A future signed and notarized distribution unit and independently approved release catalog are still required |
| `ScreenpunkBuildHost.app` and `ScreenpunkBuildService.xpc` | Private source/test packages | `package-host.sh`/`package-xpc.sh` resolve the supplied identity to one valid Developer ID Application certificate for `77KASWDGM6` before packaging and preserve the XPC sandbox entitlement, but no production release pipeline currently publishes them | Developer ID Application plus a separately approved kit/catalog publisher identity |

To enable the existing signed release jobs, supply the iOS Apple Distribution `.p12` and password, an App Store distribution profile for `xyz.screenpunk.ios`, the Mac Developer ID Application `.p12` and password, and the App Store Connect API key fields named in the two workflow files to the `apple-release` GitHub environment. The team ID is public source configuration and is not duplicated in GitHub variables. Store private keys, `.p12` files, profile bytes and passwords only in environment secrets. The scripts import them into a temporary keychain, select an exact matching team/type identity by fingerprint, validate the iOS profile against it, and remove temporary signing material on job completion. The App Store Connect key is needed for notarization and for an optional TestFlight upload; IPA export itself does not upload.

For local development, make Apple Development signing assets for `77KASWDGM6` available to Xcode. A development build uses a different certificate/profile path from either release job. The generated Xcode projects default to `CODE_SIGNING_ALLOWED=YES`, `CODE_SIGN_STYLE=Automatic` and that team; they cannot be signed on a Mac without a matching usable identity. Keep the explicit `CODE_SIGNING_ALLOWED=NO` override for simulator/compile CI. Do not copy the Developer ID or Apple Distribution release identity into Debug settings. The Mac App Store is a separate Apple Distribution, profile and sandbox path; the existing Mac workflow is for direct Developer ID distribution.

Apple code signing does not by itself authorize the offline authoring kit. The installed build host verifies an exact Apple team and signing identifier, while the release catalog has its own approved signing key/channel and publisher entries. Configure and review those identities together before shipping a standalone CLI or BuildHost kit. An ad-hoc signature or the test publisher `TESTTEAM00` is never production trust.

No certificate creation, revocation, account login, device registration, app install/launch, notarization submission or release publication is part of source configuration. Perform an archive/export and inspect its signatures, entitlements and installed behavior only after the account assets and chosen distribution path are ready.
