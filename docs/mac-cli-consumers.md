# Mac CLI consumer integration status

The broker-attached Mac view is **staged** behind `SCREENPUNK_BROKER_GUI_PREVIEW=1` in this checkout. It is not the default app experience or a release compatibility claim. The default Mac workbench keeps its existing editing, deployment, live connection and native preview controls; it acquires the broker's exclusive controller-home owner lock before legacy bootstrap and holds it while open. A stale broker socket alone does not lock it out. The CLI's old-writer gate must exclude that legacy GUI before starting the broker. The staged view and `screenpunk-mcp` executable attach to the same per-user Workbench broker and never start their own `ControllerService` or LAN transport. Start the installed Screenpunk service through the CLI setup flow before testing the staged view or connecting an MCP client. Both attached consumers require the broker's controller home to match their configured local home; a mismatch fails closed. MCP stdio uses the ordinary broker credential and emits protocol messages on stdout.

The staged app reads the broker-selected workspace, contained projects, selected-workspace package history and separately labeled devices. Selecting a package fetches the manifest and file bytes in bounded, selection-bound broker chunks, verifies the manifest digest and every file hash, then renders an offline native WebView preview. Project inspection shows the source version, build head and source/package history. The staged GUI can create a contained web project, load an included text source file through the typed broker route, save a bounded edit with the expected source version, and build the resulting project. Create, patch and build requests carry the displayed workspace ID and selection generation; the broker checks that context inside the same selection lock used by workspace switching. An unsaved or conflicted draft requires explicit discard before project/workspace navigation or replacement by a source read; a delayed read cannot silently replace newer typing. A retained draft remains visible after selection invalidation. Manual device pairing uses the broker's begin/confirm/cancel methods and requires the person to compare the displayed code with the device before pressing **Codes Match**. Device detail, explicit status refresh, settings with revision checks, and connection inventory use typed broker routes. If verified preview material is unavailable, the app shows `preview_required`.

The staged GUI attempts a separate, connection-bound broker consumer lease, renews it while open, and releases it on detach. Its status remains **GUI identity or lease unavailable; broker reliance remains unknown** when the installed broker cannot verify production-signed GUI evidence. This checkout does not configure a production signer, so this code is not evidence that an installed GUI lease succeeds; service update/uninstall must still fail closed on unknown reliance. A trusted local connection review opens a separate `.localReview` broker connection, asks for an exact pending intent ID, presents the broker's complete escaped/redacted scope, and enables approval only after scrolling to the end. Confirmation uses the review handle on that same connection. Deny and Leave Pending are distinct actions, and uncertain results are reported as unknown. No ordinary MCP credential or claimed GUI role can approve the connection. The workflow needs a compatible installed broker and a trusted local-review credential; it has not been exercised with a real device.

The optional staged source editor is deliberately a 2,048-byte whole-file path. Larger files belong in the CLI source workflow, whose approved contract allows up to 5 MiB per file and 25 MiB per project; this staged editor is not full source-editing parity or a new native IDE. Default-mode GUI forwarding, GUI Apply and deployment parity still need release qualification. The existing native preview and explicit GUI Apply remain the intended GUI surfaces.

When another controller holds the legacy owner lock, the default app does not bootstrap a second controller. It offers **Open Compatible Workbench** only after an authenticated broker hello matches the same controller home. That explicit transition keeps the existing Mac window, sidebar and native preview canvas. It reads selected-workspace package bytes through the broker, verifies them before offline preview, reads devices through typed broker routes, and reveals registered source folders for external editing. Service mode does not call legacy `ControllerService` mutations. The existing New Screen, import, device settings and dedicated connection controls remain unavailable there until their typed provider routes are integrated. The separately staged preview remains opt-in through `SCREENPUNK_BROKER_GUI_PREVIEW=1`; its device response and settings-draft guards remain as documented in its own snapshot.

The existing window's **Apply Screen** action is enabled in service mode only when a production-verifiable GUI session is available, a pinned selected-device screen set matches the selection, a verified offline package is loaded, and no prior operation is unresolved. Apply proves the current build-head/package/source identity, opens a `.localReview` connection, registers and renews the GUI lease on that same socket, and compares the frozen plan's profile hash, installed-set hash and prior selection to fresh owner-checked device state before displaying the exact native review. It passes the plan hash and authorization-context hash to broker admission. A private interprocess journal reserves the plan/idempotency key before submission, so another GUI process cannot overwrite an unresolved Apply. A selection, lease or review failure before the broker Apply call marks that reservation failed; an error once the call may have been submitted remains unknown and blocks automatic retry. The window shows admitted, sending, received, active, failed or unknown status without calling any of those states success prematurely; **Check Apply Status** and **Reconcile** use the existing operation ID. An attempt without an operation ID offers **Look Up Apply**, which queries the broker's durable plan-ID record and never resends. If lookup cannot establish an operation, the attempt remains uncertain and blocks new Apply. Imported or older packages without source proof and packages needing full live-grant review remain unavailable. Production signer, real-device behavior and the rest of default-mode feature parity have not been qualified by the no-sign build.

The MCP adapter forwards `get_workspace`, `list_devices` and `get_device` through the broker's closed read policy. It adds explicit workspace initialization/open, contained project create/open/list/get/version history, source-CAS patch, build run/head, package history, fresh device screen-set/status, device-settings read and credential-free connection-inventory read tools. `list_dashboards`, `get_dashboard` and `validate_dashboard` read selected-workspace package metadata; `get_workspace_package_file` returns bounded base64 chunks. Package history remains historical, untrusted provenance. Patch tool schema advertises closed write/delete shapes and the broker's 5 MiB decoded per-file limit; this is separate from the staged GUI editor's 2 KiB limit. Prepare, full-set plan, review, Apply, status, plan-ID lookup and reconcile map to typed broker deployment routes. MCP Apply requires an actual JSON Boolean `approved:true` agent assertion bound to the exact plan and authorization-context hashes; it cannot claim GUI or terminal consent. Workspace/capabilities/project/plan resources use broker reads. Both Official SDK and JSON-RPC fallback dispatch through the same closed adapter; clients cannot select a broker method, credential scope, consent source or `schemaVersion`. Other catalogued legacy tools return `capability_unavailable` until a typed route preserves their semantics. `preview_dashboard` and `interact_preview` return `preview_required` without a compatible helper. A large source-chunk helper exists but has no broker socket route yet, so full source export remains unavailable. Source import, privileged connection intents and legacy catalog parity remain open work; this checkout is not full MCP feature parity.

Existing app/MCP installs require a reviewed one-time migration and old-writer exclusion before adopting the broker. Installing or launching these consumers does not move legacy projects, packages, credentials or the controller identity, and it does not silently select a visible workspace. Follow the CLI migration plan and explicit apply flow when it is available; retain the old controller home as rollback material. Unmodified older binaries remain incompatible concurrent writers. Until the broker can verify connection-bound GUI consumer evidence, service update and uninstall must treat GUI reliance as unknown and fail closed.
