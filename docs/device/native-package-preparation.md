# Immutable package preparation

`DevicePackagePreparationStore` prepares already qualified package bytes in an explicitly supplied, preexisting owned root. The caller supplies a root UUID and protected paths. Overlap, symlink traversal and unexpected contents block preparation. This store has no production default, migration, reset integration, grant admission or structural writer caller.

The framed SHA-256 content identity includes the original manifest bytes and sorted asset paths, lengths and hashes. It is distinct from the manifest's canonical deployment digest. A matching directory name is never sufficient evidence. Exact intent precedes package creation; captured directory and file identities are persisted before dependent installation. Verification checks persisted identities and bytes again.

Initialization and exact recommit explicitly acknowledge successful synchronization. Diagnostic reads never acknowledge uncertain durability. Another instance's attempted write invalidates prior in-process qualification; a fresh instance must recommit the latest terminal operation before preparing a successor. An old replay does not qualify a different current tip. Receipts are privately issued by their store instance and are package evidence, not grant or management authority.

The store retains one unresolved operation and up to 128 terminal operations without pruning their resources. Metadata is bounded to 4 MiB, content to 50 MiB, with at most 2,001 files, 4,096 directories and path depth 32. All filesystem operations use verified descriptors and reject symbolic links, special files and multiply linked regular files. Only owned storage is synchronized.

If a process dies after creating a package node but before recording its inode, a new instance preserves the orphan and blocks. It does not adopt or delete unproven content. The original live instance may retry using its retained identity. Metadata scratch repair is separate from package provenance. The implementation does not claim exclusion of hostile same-user mutation, external rollback protection, or physical power-loss qualification. Production mounting still requires a recovery policy for blocked orphan evidence and integration with structural and grant authority.

Validation: ten focused tests exercise 21 fault boundaries, cross-instance invalidation, restart repair, unknown binding residue, original manifest identity, inode replacement, symlinks, hard links, special nodes, protected sentinels, bounds and retained capacity. Full isolated Core passed 227 tests against `ff538ecc` plus the reviewed PR102 files and these three preparation files. The same source built for both arm64 and x86_64 iOS Simulator with an iOS 16 minimum and iPhone/iPad device families. This is not a signed archive or physical-device qualification.
