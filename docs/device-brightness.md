# Device brightness behavior

Brightness preferences are saved with the device's settings. While Screenpunk is
active, the device applies them locally; a connected Mac is not required.

- **System:** Screenpunk releases its override. Ambient adaptation follows the
  user's iOS Auto-Brightness setting; Screenpunk cannot enable or disable it.
- **Fixed:** Screenpunk requests the selected level and reapplies it when it
  observes an external brightness change while active.
- **Schedule:** Daily entries use minutes after midnight in the device's current
  local time zone. Each level remains in effect until the next entry. Before the
  day's first entry, the final entry from the previous day applies. There is no
  interpolation. The device reevaluates at minute boundaries, activation, and
  significant time/time-zone changes.

Travel immediately changes the schedule to the new local clock. In a spring DST
gap, the first existing minute uses the latest entry whose clock time has passed.
In the repeated autumn hour, entries run again as that wall-clock hour repeats.
No skipped time is replayed on activation; only the current level is applied.

When Screenpunk becomes inactive, changes to System, or unlinks, it restores the
brightness level captured before its current override. On the next activation it
captures the then-current system level before applying saved preferences again.
No schedule execution is promised while suspended or locked, and this feature
does not launch the app after reboot or wake a locked device.

The iOS app explicitly disables multiple scenes. Its single runtime owns the
built-in display's brightness baseline; external displays are not brightness
targets. The adapter uses public `UIScreen.brightness` on the main screen (the
only screen this API supports) and brightness-change notifications.
It suppresses notifications generated by its own writes, including clamped writes,
so the observer cannot create a feedback loop. It does not use private sensor APIs
or change the user's OS Auto-Brightness preference. A confirmed application means
the observed brightness property matches the requested level (within 0.5 percentage
points), not a measurement of the panel's emitted light. iOS can impose thermal or
display-mode limits. The controller reports an unapplied setting when an observed
value differs; saved configuration remains intact.

Raw ambient-light capability is disabled. Apple's SensorKit ambient data requires
an approved research-study entitlement that Screenpunk does not hold. System mode
is still useful with the user's OS ambient adaptation enabled.

## Verification

Core tests cover midnight wrapping, exact boundaries, unsorted input, invalid
input, spring/fall DST, travel, clock changes, fixed/scheduled transitions,
activation, baseline restoration, external changes, and notification feedback on
clamped writes. The UIKit adapter still needs physical iPhone/iPad verification:
fixed/scheduled requests with Auto-Brightness on, changing ambient conditions,
Control Center changes, lock/unlock, background/foreground, clock/time-zone edits,
Reference Mode/thermal limits, and unlink cleanup. Desktop Swift tests do not
establish physical display behavior or compile the iOS-only adapter branch.
